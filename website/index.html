on-air

Stream your computer's audio to AirPlay, Sonos, Bluetooth and this computer's own speakers. Everything stays on your LAN: there is no account and no cloud.

  • Local audio router for modern Linux, also macOS and Windows
  • One Rust core, four clients
  • MIT licensed
  • Packaged for Arch, APT, RPM, Homebrew, winget, Flatpak and Nix

What it is and why

on-air takes what your computer is playing — system audio, a microphone, a USB audio interface, or an audio CD — and sends it to the speakers you already own: AirPlay, Sonos, Bluetooth, or this computer's own speakers and headphone jack.

Good speakers already sit on the network or on the desk, yet playing a video call, a record or a CD through them usually means accounts, cloud relays or heavyweight mirroring tools. on-air is the opposite: one Rust process on your machine, a LAN-only control plane, and a direct path from your audio to your speakers. Nothing is uploaded, nothing phones home, and there is no login to create.

Everything that has a screen is a client of that one core — the terminal UI on Linux, the tray app on macOS and Windows, the phone remote, and the Omarchy 4 patchbay panel. They own no playback. If every UI is closed, audio keeps streaming; if the core is stopped, nothing plays. That single owner is what keeps routing predictable.

What ships today

Everything on this page is in the repository today. Where something is still in flight, it is labelled — the honest list of what is not there yet is in the roadmap.

  • One core, many clients

    The core is one Rust process (packages/core, binary on-air-core) exposing an HTTP + WebSocket control plane on port 47990. The terminal UI, tray app and phone remote are all clients of it and own no playback.

  • Every source

    System audio (what the computer is playing), microphones, USB audio interfaces, or an audio CD with a transport that can seek and eject.

  • Every speaker

    AirPlay, Sonos, Bluetooth and this computer's own speakers. Streaming to Sonos and AirPlay points the speaker at a WAV stream the core serves under a per-activation nonce; Bluetooth writes to the OS audio sink. The terminal, tray and phone clients play to one output at a time; the Omarchy patchbay routes to groups of outputs.

  • Stereo end to end

    Stereo is carried as interleaved L16 stereo through capture, the EQ (per-channel filter state), the resampler and the radio WAV. Mono destinations get an (L+R)/2 downmix; destinations with more than two channels get their extra channels silent.

  • Omarchy 4 patchbay panel

    A native Qt Quick patchbay panel with input mixes, output groups and hanging physics cables. Cables are simulated with Verlet integration and gravity; the panel owns no audio and can close or reload during playback.

  • Phone remote

    The phone remote pairs over the LAN with a PIN and a bearer token; pairing survives restarts on both ends. It finds the host on the subnet or takes an address you type, and shows the same mixer as the desktop.

  • Mixer and tuning

    Five-band EQ, per-direction sample-rate selection, a level meter, CD transport, capture-buffer tuning, and an on-device audio benchmark that recommends a capture buffer.

  • Packaged everywhere

    Arch and AUR, APT, RPM, a Homebrew tap, winget, Flatpak, Nix (with a NixOS module), and an Omarchy installer that builds and enables the service.

How it works

The core owns the whole audio path. An exclusive session captures audio, runs it through the EQ and a resampler, publishes interleaved stereo L16 PCM on an in-process bus, and owns exactly one sender at a time. Sonos and AirPlay senders point the speaker at a WAV stream the core serves under a fresh nonce per activation, so a URL from an earlier activation goes dead; the Bluetooth sender writes to the OS audio sink.

The only way in is the control plane: HTTP and WebSocket on port 47990. Remote clients pair with a PIN and then use a bearer token. The clients read state, subscribe to events, and ask for changes — they never touch audio devices themselves.

  1. Capture — system audio, a microphone or USB interface, or an audio CD is captured as interleaved stereo frames.
  2. DSP — a five-band EQ with per-channel filter state and a channel-aware resampler shape the signal; left and right stay apart all the way through.
  3. Send — one sender at a time. Sonos and AirPlay pull /stream/<nonce>/audio.wav, a WAV stream served only while that activation is live; Bluetooth writes to the OS audio sink.
  4. Control — clients pair with a PIN and then a bearer token and drive the core over HTTP and WebSocket on port 47990.
  5. Patchbay (Linux) — the Omarchy panel adds a separate graph over PipeWire/PulseAudio buses: input mixes and output groups fan out independently, with their own timing. Synchronised playback across protocols is on the roadmap.

Install

Release status. Only v0.1.0 is published today. The commands below that build from a clone work now; the channels that download release assets (the Homebrew cask, the APT .deb, the RPM URL, the winget installer) refer to 0.2.0 assets and await the published v0.2.0 release. This is exactly the note in INSTALL.md; until that release exists, build from a clone or from source.

Omarchy / Arch — recommended on Linux

From a clone, with Rust and base-devel installed. The installer builds your working tree, installs it as a pacman package, enables the systemd user service and prints the Omarchy snippets. 

git clone https://github.com/tsonubin/on-air.git && cd on-air
packaging/omarchy/install.sh      # makepkg, sudo pacman -U, enable the service, print the snippets
on-air                            # the terminal UI; `on-air --help` for the subcommands

On Omarchy 4 an optional native patchbay panel can be enabled with sh packaging/omarchy/install-plugin.sh --enable.

Desktop app on Linux

packaging/install.sh            # Arch: a pacman package. Otherwise Flatpak, else ~/.local
packaging/install.sh yay        # build and install a pacman package (on-air-desktop)
packaging/install.sh flatpak    # per-user Flatpak, com.shay.on-air
packaging/install.sh user       # ~/.local/bin and ~/.local/share, no package manager

Nix

nix run github:tsonubin/on-air            # on-air-core
nix build github:tsonubin/on-air          # ./result/bin/on-air-core
nix develop github:tsonubin/on-air        # rustc, cargo, pnpm, Linux GUI deps

A NixOS module is exported as nixosModules.default (services.on-air-core.enable = true;, with port and mock options).

Build from source — any platform

pnpm install
cargo run --locked --release -p on-air-core --bin on-air-core   # headless core
cargo build --locked --release -p on-air-tui                    # target/release/on-air (Linux UI)
pnpm --dir apps/desktop tauri build                             # desktop app bundles

Release-asset channels — awaiting v0.2.0

These commands are real today but expect assets from the next release.

macOS, Homebrew tap:

brew tap tsonubin/on-air https://github.com/tsonubin/on-air.git
brew install --cask on-air        # the tray app, from the release .dmg
brew install on-air-core          # the headless core, built from source

Windows, winget (from a clone, once the NSIS installer is on the release):

winget install --manifest packaging/winget

Debian / Ubuntu, APT (downloads the desktop .deb from the release):

packaging/apt/install.sh          # downloads and apt-installs for this architecture

Fedora / RHEL, RPM (from the release):

VERSION=0.2.0
sudo dnf install "https://github.com/tsonubin/on-air/releases/download/v${VERSION}/on-air-desktop-${VERSION}-1.x86_64.rpm"

The full asset list, checksums and every other channel (Flatpak, winget manifests, AUR recipes) are documented in INSTALL.md.

Roadmap

Direction, not promises — each item below is work that is happening now or is planned. None of it is shipped; nothing on this list should be read as a feature of the current release.

  • In progress

    True stereo across every client

    The core streams true stereo to speakers today (PR #10); the remaining work is carrying left and right apart through every client surface.

  • Planned

    Mixed-protocol synchronised playback

    Playing to AirPlay, Sonos, Bluetooth and local outputs at the same time, aligned at fine granularity. Today's patchbay groups run on independent timing and do not promise synchronised playback.

  • In progress

    Cleaner audio

    Dither on the L16 quantisation is in review (PR #11, rounds to nearest with TPDF dither instead of truncating). Higher-quality resampling and benchmark-driven quality presets are planned.

  • Planned

    Drag-only cable patchbay

    Connecting patchbay cables by dragging only, in the Omarchy panel.
