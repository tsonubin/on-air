## What I am landing

**One bug, fixed properly: `bluetoothctl` is unbounded on the `/api/outputs`
request path.**

`packages/core/src/sender/bluetooth_host.rs` shells out to `bluetoothctl` with
no timeout to list paired devices. On a host where the system bus never answers
— no bluetoothd, or a bus that is wedged — that call **never returns**, and
because `list()` backs `GET /api/outputs`, the request hangs forever. I have seen
exactly this: `tests/serve_integration.rs::serve_responds_to_status_over_http`
blocks indefinitely on this box, and a control run on pristine `origin/main`
reproduced it.

It is a small fix, and it is the kind of fix that should land on its own rather
than be buried inside a 2884-line PR. Yes, PR #16 carries an equivalent change;
a focused standalone commit is still the better shape for something this
user-visible, and if #16 merges first this simply drops out.

The same function is also called for `bluetoothctl info <addr>` per device, so a
wedged bus costs one hang per device, not one overall.
